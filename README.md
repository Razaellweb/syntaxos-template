# syntaxos-template

The canonical Next.js product template used by the SyntaxOS backend agent to build full-stack applications.

## Structure

```
src/
├── app/                    Next.js 14 App Router entry
│   ├── layout.tsx
│   ├── page.tsx
│   └── globals.css
└── lib/
    └── services/           Self-contained service wrappers (the good stuff)
        ├── manifest.json           Registry of available wrappers
        ├── manifest.schema.json    JSON Schema for the manifest
        ├── errors.ts               Shared error class definitions
        ├── README.md               Wrapper contract & usage docs
        └── <provider>.ts           One thin-shim wrapper per provider
```

## How this template is used

The SyntaxOS backend agent clones this repository into an E2B sandbox at the start of every product build. The agent has tools to:

- `list_template_files` — browse the template tree
- `read_template_file` — inspect files before copying
- `copy_template_to_product` — copy files into the product sandbox

The **services** directory is the primary source of reusable code. Each file under `src/lib/services/` wraps one provider's official SDK and is designed to be copy-and-drop: one file, zero cross-file imports, reads credentials from `process.env`, exports both a class and a default singleton.

See `src/lib/services/README.md` for the full wrapper contract.

## How wrappers get here

Wrappers are generated by the SyntaxOS wrapper-generation pipeline:

1. A provider's schema is loaded from the knowledge base.
2. The LLM generates a single TypeScript file that shims the provider's official SDK.
3. The file is type-checked against this template's `tsconfig.json`.
4. `manifest.json` is updated with the wrapper's metadata (npm deps, env vars, category).
5. The pipeline commits and pushes to `main`.

Once pushed, every product built afterward has access to the new wrapper automatically.

## Environment variables

Each wrapper declares its required environment variables in `manifest.json`. The backend agent reads this manifest at deploy time and prompts the product user for each variable. There is **no `.env.example`** — the manifest is the source of truth.

## Conventions

- **Path alias**: `@/*` → `src/*`
- **Wrapper imports in product code**: `import { paystack } from "@/lib/services/paystack"`
- **Error handling**: `import { ServiceAuthError, ServiceRateLimitError, ServiceNotFoundError } from "@/lib/services/errors"`

## Not included

This template deliberately ships with **no wrappers by default**. The wrapper-generation pipeline populates `src/lib/services/` over time. The only files that live here at bootstrap are:

- `manifest.json` (empty)
- `manifest.schema.json`
- `errors.ts`
- `README.md`
